# Политика поддержки KADR (задание 15, часть Б)

## 1. Минимальная версия ОС (minSdk)
- Сейчас: **minSdk 24 (Android 7.0)**, targetSdk 35, compileSdk 35.
- Повышение minSdk рассматривается раз в год (январь), если доля устройств ниже нового minSdk среди активных пользователей KADR (Firebase Analytics) < 3%, или библиотека/требование безопасности требует новый API.
- Порядок: объявление в «Что нового» и на странице релиза за 90 дней → последняя версия для старых ОС помечается LTS и получает только исправления безопасности 6 месяцев → повышение minSdk = новая MAJOR-версия.

## 2. Обновление зависимостей и targetSdk
| Что | Когда | Как |
|---|---|---|
| targetSdk | Не позднее 31 августа каждого года (требование Google Play: новая версия Android в течение года) | Ветка `chore/target-sdk-XX`, прогон CI + ручная матрица |
| AGP, Gradle, Firebase BoM | Ежеквартально | Отдельный PR, CHANGELOG `Changed` |
| Критические уязвимости (CVE) | В течение 7 дней | PATCH-релиз |
| JDK для CI | При выходе нового LTS | Проверка lint/R8 совместимости |

## 3. Жизненный цикл версий
| Статус | Определение | Поддержка |
|---|---|---|
| Current | Последняя MINOR (сейчас 1.2.x) | Новые функции и исправления |
| Maintenance | Предыдущая MINOR (1.1.x) | Только критические исправления 3 месяца |
| LTS | Последняя версия перед повышением minSdk/MAJOR | Безопасность 6 месяцев |
| EOL | Остальные | Нет; `min_supported_version_code` в config.json вынуждает обновиться |

## 4. Резервное копирование
| Объект | Где | Частота | Проверка восстановления |
|---|---|---|---|
| Upload keystore `kadr-upload.jks` + пароли | Зашифрованный архив (AES-256) в облаке + офлайн-флешка; пароли в менеджере паролей отдельно | При создании/ротации | Раз в полгода: подписать тестовую сборку из копии |
| Репозиторий | GitHub + локальные клоны + еженедельный `git bundle` во внешнее хранилище | Еженедельно | `git clone` из bundle |
| Секреты CI | Дублируются в менеджере паролей | При изменении | — |
| google-services.json | Firebase Console (всегда можно скачать заново) | — | — |

## 5. План реагирования на инциденты
| Уровень | Пример | Реакция (SLA) |
|---|---|---|
| SEV-1 | Сбой при запуске/бронировании у многих, утечка данных | Подтверждение ≤ 1 ч, остановка раздачи и kill switch ≤ 2 ч, hotfix ≤ 24 ч |
| SEV-2 | Функция не работает, есть обходной путь | ≤ 1 рабочий день, исправление в ближайшем PATCH |
| SEV-3 | Косметика | В плановом MINOR |

Шаги: 1) обнаружение (Crashlytics alert, отзывы, issue) → 2) оценка уровня → 3) сдерживание: halt rollout (`rollout_percent: 0`), флаг функции `false`, при необходимости `min_supported_version_code` → 4) hotfix-ветка от тега, PATCH + versionCode → 5) раздача 100% (hotfix не требует долгого staged rollout) → 6) postmortem в issue: причина, время обнаружения/восстановления, меры.

## 6. Уязвимости
- Сообщения об уязвимостях — приватно через GitHub Security Advisories (не публичные issue).
- Подтверждение ≤ 48 ч, исправление критических ≤ 7 дней, публикация advisory после выхода исправления.
- Dependabot alerts включены для зависимостей Gradle и GitHub Actions.
